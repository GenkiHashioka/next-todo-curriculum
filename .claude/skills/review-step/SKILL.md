# 受講者のステップをレビューする

このスキルは**講師（運用者）が使う**ものです。
受講者のステップ提出をレビューし、**通す／確認する／差し戻す**の判断材料をまとめます。

> ⚠️ このリポジトリ直下の `AGENTS.md` は**受講者向けのチューターモード**です。
> レビュー時はそれではなく、**このスキルと `.docs/curriculum/INSTRUCTOR_GUIDE.md`** に従ってください。

---

## 前提を確認する

引数でブランチ名（例: `hashioka-step-2`）を受け取ります。
指定がなければ、レビュー対象のブランチ名をユーザーに尋ねてください。

ブランチ名から **受講者名** と **ステップ番号** を読み取ります。

まず [`.docs/curriculum/INSTRUCTOR_GUIDE.md`](../../../.docs/curriculum/INSTRUCTOR_GUIDE.md) を読み、
レビュー基準（特に「許容する / 理由を確認する / 許容しない」の 3 段階）を把握してください。

---

## 手順

### 1. 差分を取得する

そのステップのベースからの差分を見ます。

```bash
git fetch origin
# Step 1 は main が起点。Step 2 以降は受講者のベースブランチが起点
git diff --stat origin/{受講者名}...origin/{受講者名}-step-{N}   # Step2以降
git diff --stat origin/main...origin/{受講者名}-step-1           # Step1
```

起点が分からなければ `git merge-base` で確認します。
変更ファイル一覧を把握してから、実際の差分を読みます。

### 2. 機械的にチェックできることを確認する

以下は **判断の余地がない** ので、まず自動で確認します。

| 確認項目 | 方法 |
|---|---|
| 触ってはいけない層を変更していないか | 差分に `src/app/api/` `src/domain/` `src/infrastructure/` `src/usecases/` `src/lib/` が含まれないか |
| ビルドが通るか | `npm run build`（型エラーはここで出る） |
| `main` に直接コミットしていないか | `git log origin/main --oneline -5` に受講者のコミットが無いか |
| ブランチ名が規約どおりか | `{受講者名}-step-{N}` の形式か |

### 3. ステップの制約を確認する

**このカリキュラムで最も重要なチェック**です。段階的に学ぶ設計が崩れるため、
制約違反は差し戻します。

| Step | 使ってはいけないもの | 確認方法 |
|:---:|---|---|
| 1 | HeroUI、サーバーコンポーネント、コンポーネント分割 | `@heroui/react` の import が無いか。全ファイルに `'use client'` があるか |
| 2 | HeroUI、コンポーネント分割 | `@heroui/react` の import が無いか。`features/*/components/` が作られていないか |
| 3 | コンポーネント分割 | `features/*/components/` が作られていないか |
| 4 | — | — |

### 4. ステップ別の観点で読む

`INSTRUCTOR_GUIDE.md` の「ステップ別の観点」に沿って差分を読みます。
特に見るべき点:

- **Step 1**: `useState` / `useEffect` の使い方、ローディング・エラー表示の有無
- **Step 2**: `'use client'` が必要な箇所だけに付いているか、`params`/`searchParams` を `await` しているか
- **Step 3**: **v2 の書き方が混ざっていないか**（`CardBody` / `useDisclosure` / `SelectItem` / `color=` / `isLoading`）、
  `validationBehavior="aria"` が付いているか、`className` で HeroUI の既定スタイルを打ち消していないか
- **Step 4**: 1コンポーネント1責務か、Props の型定義があるか

### 5. 「違い」を 3 段階で仕分ける

**参考実装（`reference/v3-complete`）と違うこと自体は問題ではありません。**
必ず次の 3 段階で仕分けてください。

- ✅ **許容**: レイアウト・配色・分割粒度・命名・文言の違い → 通す
- 🤔 **要確認**: 未習のライブラリ導入、大きく異なる設計判断 → 理由を聞く
- ❌ **差し戻し**: ステップ制約違反、触ってはいけない層の変更、ビルド不通、
  構造的におかしい実装（Server Component で `useState`、画面から直接 DB 等）

> 判断に迷ったら「**好みの違いか、理解の欠落か**」で切り分けます。

### 6. 理解度を確認する質問を作る

**このカリキュラムでは、説明できることが完了条件です。**
差分の中から、**その受講者が書いた具体的なコードに紐づく質問**を 3〜5 個作ってください。

一般論ではなく、実際のコードを指して聞きます。

良い質問の例:
- 「`TodoListPage.tsx` の `useEffect` の依存配列に `page` を入れているのはなぜ？外すとどうなる？」
- 「ここを Server Component にした理由は？クライアントのままだと何が困る？」
- 「このエラーハンドリング、失敗したときユーザーには何が見える？」
- 「`{具体的な箇所}` を別の書き方にするとしたら、どうする？」

AI 丸投げの兆候（教材にない書き方が突然出る、コミット間で粒度や命名の癖が変わる）が
あれば、その箇所を重点的に聞く質問を含めます。

### 7. レビュー結果をまとめる

次の形式で出力してください。**指摘には必ず理由を添えます。**

```markdown
## レビュー結果: {ブランチ名}（Step {N}）

### 判定
✅ 通過 / 🤔 要確認 / ❌ 差し戻し

### 良かった点
- （具体的に挙げる。ここを飛ばさない）

### 差し戻しが必要な点
- **{指摘}** — {理由}
  `{ファイル}:{行}`

### 確認したい点（理由を聞く）
- **{指摘}** — {なぜ気になるか}

### 理解度の確認に使う質問
1. …
2. …

### 参考
- 制約違反: なし / あり（内容）
- ビルド: 通る / 通らない
- 触ってはいけない層の変更: なし / あり
```

---

## レビューの心構え

- **参考実装と違う＝間違い、ではありません。** 好みの違いは通します。
- **良かった点を必ず書きます。** 指摘だけだと受講者が萎縮します。
- **指摘には理由を添えます。** 「こう直して」ではなく「こうだとこう困るので」。
- **説明できない箇所こそが伸びしろ**です。詰めるのではなく、一緒に読み解く materials として扱います。
