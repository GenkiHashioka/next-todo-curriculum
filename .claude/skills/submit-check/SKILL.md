# 提出前の自己チェック

**レビューに出せる状態かどうか**を確認します。各ステップの実装が終わったら実行してください。

---

## ⚠️ このスキルの役割（重要）

検査そのものは `bun run submit-check`（[scripts/submit-check.mjs](../../../scripts/submit-check.mjs)）
が行います。**あなたの仕事は、その結果を読み解いて受講者に説明すること**です。

- ここで見るのは、**機械的に判定できることだけ**です。
  ビルドが通るか、ステップの制約を守っているか、といった「間違いようがない」部分です。
- **実装の中身が良いかどうかは判定しません。** それはレビューで講師と話す部分です。
- **通っても「合格」ではありません。** 「レビューに出せる状態になった」というだけです。

### 🚫 見つけた問題を、代わりに直さないこと

問題が見つかったら、**どこに何があるかと、なぜそれが問題なのかを伝えて、そこで止まってください。**
修正コードを書いてはいけません。ファイルも編集しないでください。

> なぜか: ここで直してしまうと、受講者は「なぜそれが問題なのか」を知らないまま先へ進みます。
> このカリキュラムの目的は、動くものを作ることではなく、自分で書けるようになることです。

受講者が「直し方が分からない」と言った場合は、リポジトリの `AGENTS.md`（チューターモード）に
従って、答えではなくヒントを段階的に出してください。

---

## 手順

### 1. チェックを実行する

```bash
bun run submit-check
```

ビルドを含むため 1 分ほどかかります。終了コードは、直すべき問題があれば 1、なければ 0 です。

> スクリプトが無い、または動かない場合は、受講者のブランチが古い可能性があります。
> `main` から最新を取り込むよう案内してください。

### 2. 結果を読み解く

出力は `OK` / `確認` / `NG` の 3 段階です。**`NG` だけが直す対象**です。

特に説明が必要になりやすいもの:

| 項目 | 伝えること |
|---|---|
| **ビルド NG** | エラーメッセージの**ファイル・行・「何が期待されて何が来たか」**を噛み砕く。原因の説明はしてよいが、**修正コードは書かない** |
| **ステップ制約 NG** | なぜその制約があるかを添える（例: Step 1 で素の Tailwind を書くのは、後で HeroUI が何を肩代わりしているか分かるようにするため） |
| **HeroUI v2 の書き方 NG** | 検索や生成 AI の情報は v2 向けが多いことを伝え、[対応表](../../../.docs/heroui-v2-to-v3-migration.md)を案内する |
| **触ってはいけない層 NG** | フロントの課題なので、API を書き換えて解決するのは筋が違う、と伝える |

### 3. 「確認」（⚠️）は必ず中身を見る

**`v2 らしき Props` が `確認` になった場合、そのまま指摘してはいけません。**

`isLoading` / `color` / `onValueChange` などは、**受講者が自分で作ったコンポーネントの
Props としても普通に使われます**。その場合はまったく問題ありません。

出力された各行について、**その Props を受け取っているコンポーネントが
`@heroui/react` からインポートされているか**を実際にファイルを読んで確認してください。
HeroUI のコンポーネントに付いている場合だけが指摘対象です
（v3 では `color=` → `variant=`、`isLoading=` → `isPending=`）。

`Lint` の `確認` は、多くが `bun run check` で自動修正できます。
**受講者自身が実行できるよう案内**してください（こちらで実行しない）。

### 4. 機械では判定できないことを念押しする

スクリプトの出力末尾にも出ますが、次の 3 つは自動では確認できません。

- 実際に画面を触って、実装した機能がひととおり動くか
- エラーになったとき、画面に何が出るか
- **自分が書いたコードを、人に説明できるか**

特に最後のひとつは、このカリキュラムで一番大事な完了条件です。
「ここは何をしている処理？」と 1〜2 問その場で聞いてみると、受講者自身が
説明できるかどうかに気づけます。**詰問にはせず、詰まったら一緒に読み解いてください。**

### 5. 通ったら、次に何をするかを伝える

```
1. GitHub で PR を作成（from: {名前}-step-N → to: {名前}）
   ⚠️ main に向けない
2. CI（ビルド・テスト）が緑になるのを確認
3. レビューを依頼
```
