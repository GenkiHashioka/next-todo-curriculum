# 講師ガイド（運用・レビュー規約）

このカリキュラムを**運用する側**のためのドキュメントです。
受講者は読む必要がありません（受講者向けは [README](../../README.md) と各 Step 教材）。

> ⚠️ **AI エージェントでレビューする場合の注意**
> リポジトリ直下の `AGENTS.md` は**受講者向けのチューターモード**です。
> 講師としてレビューする際は、このファイルを明示的に読ませてください。
> 例: 「`.docs/curriculum/INSTRUCTOR_GUIDE.md` に従ってレビューして」

## 1. リポジトリの構成

| ブランチ | 役割 |
|---|---|
| `main` | **スターター**（`src/features/` が空）。受講者の出発点。**不変** |
| `reference/v3-complete` | **参考実装**（実装例のひとつ・唯一の正解ではない）。Vercel にデプロイ済み |
| `{受講者名}` | 受講者のベースブランチ |
| `{受講者名}-step-N` | 各ステップの作業ブランチ |

```
main（不変）
 └─ hashioka
     ├─ hashioka-step-1 → レビュー通過後 hashioka へマージ
     ├─ hashioka-step-2
     ├─ hashioka-step-3
     └─ hashioka-step-4
```

### ブランチの保護について

リポジトリを **public 化したことで GitHub のブランチ保護が使えるようになりました**
（ブランチ保護は public リポジトリなら Free プランでも利用できます）。
`main` と `reference/v3-complete` の**両方**に設定済みです。

| 設定 | 値 |
|---|---|
| Require a pull request before merging | ON（**Required approvals: 0**） |
| Require status checks to pass | ON（必須チェック: **`build & test`**） |
| Do not allow bypassing the above settings | ON（**管理者にも適用**） |
| force push / ブランチ削除 | 禁止 |

**Required approvals を 0 にしているのは意図的**です。1 以上にすると Dependabot が
自分の PR を自己承認できず、patch / minor の自動マージが毎回止まります。
0 でも「PR を経由すること」自体は強制されるため、直接 push の禁止は達成できます。

> ⚠️ **これは飾りではありません。** 以前はブランチ保護が使えず、
> `gh pr merge --auto` が CI の成功を待たずにマージしていたため、
> **CI が赤い Dependabot PR がそのまま `main` に入る**事故が起きていました（PR #12）。
> 必須ステータスチェックが設定されて初めて、auto-merge は CI の完了を待ちます。

補助的に、次の 2 つも維持しています。

1. **git hook**（`.githooks/pre-push`）— `main` への push を拒否する
   **Dev Container の初回セットアップで自動的に有効化される**ため、
   受講者が実行し忘れる余地はありません（`.devcontainer/scripts/post-create.sh`）。
   手元で早い段階で気づけるという意味で、サーバー側の保護とは役割が違います。
   > ℹ️ コンテナを使わずに clone した場合は有効になりません。
   > 手動で有効化する場合は `git config core.hooksPath .githooks`。
2. **規約** — README と `AGENTS.md` で「`main` へ直接 push しない」と明示

> ℹ️ 「push できる人を指名する」設定（Restrict who can push）は
> **Organization 所有のリポジトリ限定**のため、現在は使えません。
> 代わりに「PR 必須 + 管理者にも適用」で全員に同じ制約をかけています。

## 2. 受講者の受け入れ手順

1. GitHub でリポジトリへコラボレーター招待（**Write** 権限）
2. 事前に用意してもらうもの
   - **Docker Desktop**
   - **VS Code**（または Cursor）+ Dev Containers 拡張
3. README の「セットアップ」に沿って環境構築してもらう
   - clone →「Reopen in Container」→ `bun run dev` の 3 手
   - `.env` の作成・`JWT_SECRET` の生成・`core.hooksPath` の設定・
     **動作確認用の管理者アカウント（`admin` / `password`）の作成**は
     **コンテナの初回セットアップで自動的に行われる**（手作業なし）
4. 自分のベースブランチを作ってもらう
   ```bash
   git checkout main
   git checkout -b {受講者名}
   git push -u origin {受講者名}
   ```
5. [基本設計書](./00_basic_design.md) を読んでもらってから Step 1 へ

> 💡 **最初のつまずきポイントは環境構築**です。Dev Container 化でかなり減りましたが、
> 残っている落とし穴は次の 2 つ。受け入れ時に必ず口頭で伝えてください。
>
> - **Windows の受講者は WSL2 の中に clone する。**
>   Windows 側（`C:\Users\...`）に置くと動作が極端に遅くなり、「重い」で離脱します
> - **初回は 5〜15 分かかる。**
>   何も起きていないように見えて不安になるので、先に伝えておく
>
> 初回だけ画面共有で一緒に立ち上げると確実です。

> 🔑 **管理者アカウントについて**
>
> DB は空から始まるため、Step 1 の「管理者機能ページ（`/users`）」を
> 自分で登録したアカウント（`role: 4`）では確認できません。
> そこで動作確認用に `admin` / `password`（ADMIN）を自動作成しています。
> 消えた場合は `bun run seed:admin` で作り直せます。
>
> ローカル限定の学習用アカウントです。デプロイ環境（Vercel / Neon）では作られないので、
> そちらは [deploy-vercel.md](../deploy-vercel.md) のとおり SQL で昇格させてください。

## 3. レビューの進め方

### 基本方針

**動くかどうかより、理解しているかを見ます。**
このカリキュラムの目的は完成させることではなく、書けるようになることです。

### レビューの流れ（PR ベース）

```
受講者: bun run submit-check   ← 機械的な問題はここで潰れる
      ↓
受講者: PR 作成（{名前}-step-N → {名前}）
      ↓
自動:   CI（build + test）が走る
      ↓
講師:   /review-step {PR番号}   ← 理解度の確認に集中
      ↓
講師:   PR を Merge
```

> 💡 **機械的なチェックは受講者側で済んでいる前提**です。
> 各 Step 教材の末尾で、提出前に `bun run submit-check` を実行するよう案内しています
> （Claude Code なら `/submit-check` でも可）。ブランチ・ビルド・ステップ制約・
> HeroUI v2 の混入はここで潰れます。**講師は理解度の確認に集中してください。**
>
> **CI が赤い PR は、中身を読む前に差し戻して構いません。**
> 提出前チェックを実行していない可能性が高く、講師が読む段階ではありません。

> ⚠️ **PR の向き先を確認してください。** `main` に向いている PR は差し戻します
> （`main` はスターターなので変更しません）。正しい向き先は受講者のベースブランチです。

> ℹ️ **CI はすべての PR で走ります**（ドキュメントだけの変更でも）。
> 以前は無料枠の節約のためドキュメントのみの変更を除外していましたが、
> ①public 化により Actions が無料になったこと、②必須ステータスチェックを
> 設定すると「CI がスキップ ＝ チェックが報告されない」状態になり
> **ドキュメントのみの PR が永久にマージできなくなる**ことから、除外をやめました。

### ⚠️ `reference/v3-complete` は「唯一の正解」ではない

参考実装はカリキュラム作成者が書いた**実装例のひとつ**です。
**それと違うことを理由に差し戻さないでください。**

受講者には「考えて Todo アプリを作りきる」ことを求めています。
違いは、次の 3 段階で判断します。

#### ✅ 許容する（むしろ歓迎したい違い）

- レイアウト・配色・余白・文言の違い
- コンポーネントの分割粒度（Step 4 で「ここまで分けた／分けなかった」の判断差）
- 状態管理の細かい書き方（`useState` の持たせ方、変数名 など）
- エラーメッセージの表現
- 要件を満たしたうえでの UI の工夫・追加

> これらは**設計判断**です。理由を説明できるなら、それは受講者の正解です。
> むしろ「なぜそうしたか」を聞ける良い機会になります。

#### 🤔 理由を確認する（聞いたうえで判断）

- 教材で扱っていないライブラリ・パターンの導入
  → 「なぜ必要だと思ったか」を聞く。妥当なら OK
- 参考実装と大きく異なる設計判断
  → 意図があるなら OK。「なんとなく」なら一緒に考える
- 極端に細かい／粗いコンポーネント分割
  → 分け方の基準を説明できるかを確認

#### ❌ 許容しない（差し戻す）

- **ステップの制約違反**（Step 1 で HeroUI を使う、Step 3 でコンポーネント分割する 等）
  → 段階的に学ぶ設計が崩れるため
- **触ってはいけない層の変更**（`src/app/api/`、`domain/`、`infrastructure/`、`usecases/`）
  → フロントの課題なので、バックエンドを書き換えて解決するのは筋が違う
- **型エラー・ビルドが通らない**
- **構造的におかしい実装**（動いていても）
  - Server Component で `useState` を使おうとしている
  - 画面から DB へ直接アクセスしようとしている
  - 認証チェックを回避している
- **本人が説明できない**（理解を伴っていない）

> 判断に迷ったら「**これは好みの違いか、それとも理解の欠落か**」で切り分けてください。
> 好みなら通す。理解の欠落なら、そこを一緒に埋める。

### 各ステップ共通のチェック

- [ ] ブランチ名が規約どおりか（`{名前}-step-N`）
- [ ] `main` に直接コミットしていないか
- [ ] `bun run build` が通るか（型エラーがないか）
- [ ] 触ってはいけない場所（`src/app/api/`, `domain/`, `infrastructure/`, `usecases/`）を
      変更していないか
- [ ] コンソールにエラーが出ていないか
- [ ] **本人が実装を説明できるか**（後述）

### ステップ別の観点

#### Step 1: クライアントコンポーネント
- [ ] すべて `'use client'` で実装されているか
- [ ] **HeroUI を使っていないか**（Tailwind CSS のみ）
- [ ] 1ページ = 1ファイルになっているか（この時点では分割しない）
- [ ] `useState` / `useEffect` の使い方が理解できているか
- [ ] ローディング中・エラー時の表示があるか

#### Step 2: サーバーコンポーネント
- [ ] データフェッチがサーバー側に移っているか
- [ ] `'use client'` が必要な箇所（フォーム・イベント）だけに付いているか
- [ ] `params` / `searchParams` を `await` しているか（Next.js 16）
- [ ] Server Actions（`src/lib/api.ts`）を使えているか

#### Step 3: HeroUI v3
- [ ] **v2 の書き方が混ざっていないか**（`CardBody`、`useDisclosure` など）
- [ ] `className` で HeroUI の既定スタイルを打ち消していないか
- [ ] フォームに `validationBehavior="aria"` が付いているか
- [ ] バリデーションエラーが実際に画面に出るか

#### Step 4: コンポーネント分割
- [ ] 1コンポーネント1責務になっているか
- [ ] Props の型が定義されているか
- [ ] 分割しすぎ / 足りない、のバランスは妥当か
- [ ] 共通ヘッダーが `src/components/` に切り出されているか

## 4. 理解度の確認（最重要）

コードが動いていても、**説明できなければ次のステップに進めない**方針です。
レビュー時に、実装について質問してください。

**質問の例**:
- 「この `useEffect` の依存配列に `x` を入れているのはなぜ？」
- 「ここを Server Component にした理由は？」
- 「このエラーが出たとき、どうやって原因を見つけた？」
- 「この部分、別の書き方だとどうなると思う？」

説明できない箇所があれば、**そこを一緒に読み解く**のがレビューの中心になります。

### AI に丸投げした兆候

技術的に完全な判別はできませんが、次のような場合は理解度を丁寧に確認してください。

- 教材で扱っていない書き方・ライブラリが突然使われている
- コードの粒度や命名の癖が、コミット間で不自然に変わる
- 動くが、そのステップの制約を無視している（Step 1 なのに HeroUI を使う等）
- 本人が処理の流れを説明できない

> AI の利用自体は禁止していません（`AGENTS.md` でチューターとして振る舞うよう指示済み）。
> **問題は「理解しないまま進むこと」**なので、そこだけ確認します。

## 5. ステップ完了の判定

以下がすべて満たされたら、PR をマージして次のステップへ。

1. そのステップのチェック項目を満たしている
2. **CI が緑**（ビルド・テストが通っている）
3. **実装内容を本人が説明できる** ← ここが本体
4. 動作確認が取れている（実際に触って確認）

マージは **PR 画面の Merge ボタン**、または:

```bash
gh pr merge {PR番号}
```

受講者は次のステップのブランチを、マージ後のベースブランチから切ります。

```bash
git checkout {受講者名}
git pull
git checkout -b {受講者名}-step-2
```

> 3 は機械では判定できません。**動いていても説明できなければ通しません。**
> 詰まった箇所は差し戻すのではなく、その場で一緒に読み解くのがおすすめです。

## 7. 依存関係の更新

**自動化されているのは PR の作成とマージまで**です。
**その先の工程（下記「作業手順」の②〜④）は、パッチ / マイナーでも必要です。**

| 種別 | マージ | マージ後の作業（②〜④） |
|---|---|---|
| パッチ / マイナー | CI が通れば**自動** | **必要**（版数記述の追従・バックマージ） |
| メジャー | **手動**（内容を確認して判断） | 必要。加えて破壊的変更の調査を丁寧に |
| TypeScript 7 | 現在は対象外。使えるようになったら月次チェックが Issue で通知 | — |

> ⚠️ **「マイナーだから何もしなくていい」ではありません。**
>
> PR #12 は `safe-updates`（パッチ / マイナーのみ）のグループでしたが、
> `next` が 16.2.12 → **16.3.0** に上がったことで**教材の版数記述が古くなり**、
> さらにキャレット範囲内で推移的依存が動いたことで**型チェックが 9 件壊れました**。
> メジャー更新は 1 件も含まれていません。
>
> 自動化されているのは「マージまで」で、その先は人の作業です。

メジャー更新の PR は自動マージされないので、CI の結果を見てからマージしてください。
UI に関わる更新は、デプロイされた画面も確認することを推奨します。

> 💡 **頻度が負担になる場合**：パッチ / マイナーは毎週来ます。毎回フルで回すのが重ければ、
> **②（版数記述の追従）は毎回、③④（バックマージ）は週次でまとめて**という運用でも構いません。
> バックマージは元々「週 1 回ほど」の想定です。

### 作業手順（スキルの呼び出し順）

依存更新は **`main` を正として、一方向に流す**のが原則です。この順序で回してください。

```
① Dependabot PR が main にマージされる（patch / minor は CI が緑なら自動）
        ↓
② /sync-doc-versions        （main）      教材の版数記述を package.json に追従 → PR → マージ
        ↓
③ /backmerge-reference      （reference） 依存を取り込み、破壊的変更を調査・修正
   └ 内部で /check-curriculum-sync を実行（教材と実装の突き合わせ）
        ↓
④ ③で教材を直した場合は、同一コミットを main 向け PR にも cherry-pick（ペアで出す）
```

各スキルの末尾に「次にやること」を書いてあるので、順に辿れば迷いません。

**②を飛ばさないでください。** `main` の教材が古いままバックマージすると、
`check-curriculum-sync` が `reference/v3-complete` 側で乖離を検出し、
「参考実装を先に直して `main` が後追い」という逆流が起きます。

**④が必要な理由**：教材は両ブランチに複製されており、内容を一致させる必要があります。
一方で教材のコード例の誤りは、実装がある `reference/v3-complete` でしか発見できません
（`main` は `src/features/` が空のスターターのため、突き合わせる実装が存在しない）。
そのため教材の修正だけは `reference` → `main` へ戻す流れになります。

> 💡 ②で差分が出なければ PR は作られません。その場合はそのまま③へ進んでください。

### `reference/v3-complete` へのバックマージ（週次・手動）

**Dependabot が対象にしているのは `main` だけ**です（`.github/dependabot.yml` に
`target-branch` の指定が無く、既定の `main` のみが対象）。自動マージされた変更も
`reference/v3-complete` には反映されないため、**週に 1 回ほど手動で取り込んでください**。

自動化はしていません。`main` はフロントエンド実装（`src/features/`）が空のスターターなので、
講師が定期的に中身を見ておく必要性自体があるためです。
（依存更新で破壊的変更が入ったとき、それが顕在化するのは実装のある
`reference/v3-complete` 側です。人の目を通す価値がここにあります）

```bash
# 1. main 側で直近マージされた Dependabot PR を確認
gh pr list --base main --state merged --search "author:app/dependabot" \
  --json number,title,mergedAt --limit 20

# 2. reference/v3-complete から作業ブランチを切る
git fetch origin
git checkout -b backmerge/$(date +%Y%m%d) origin/reference/v3-complete
```

> ⚠️ **`git merge origin/main` は実行しないでください。**
> `reference/v3-complete` の実装ファイルが **30 件削除されます**
> （`src/app/` 16 件・`src/features/` 14 件）。
>
> merge base の時点では `src/features/` に 37 ファイルありましたが、その後 `main` が
> `1d23d77`（受講者向けスターター状態の派生）で 36 ファイルを削除しています。
> Git はこれを「`main` が意図的に削除した」と解釈するため、merge すると削除が伝播し、
> `reference/v3-complete` 側が触っていないファイルは**コンフリクトにすらならず消えます**。

取り込みは cherry-pick と、依存ファイルの同期で行います。

```bash
# 3. 実装・テスト・設定の修正は cherry-pick
git cherry-pick <SHA>

# 4. 依存は package.json と bun.lock を main と同一にする
#    （個別の Dependabot コミットを cherry-pick すると中間バージョンを取りこぼす）
git checkout origin/main -- package.json bun.lock
bun install --frozen-lockfile
git add package.json bun.lock
```

`.github/workflows/ci.yml` は `main` 版で上書きしないでください。このブランチは
トリガーが `branches: [reference/v3-complete]` で、説明コメントも異なります。
`main` 側の変更内容だけを読み取り、手で適用します。

取り込んだら、依存の版が上がったことで教材のコード例が古くなっていないかを
[check-curriculum-sync スキル](../../.claude/skills/check-curriculum-sync/SKILL.md)で確認してから PR を出してください
（バージョン記述だけでなく、破壊的変更で API の書き方が変わっていないかもここで拾えます）。


## 8. テストについて（よく聞かれる点）

**「実アプリは E2E なのに、なぜここは Jest なのか」** と聞かれたときの答えです。

### テストの層構造は実アプリと一致している

| | バックエンド | フロントエンド |
|---|---|---|
| 実アプリ | `shiftapp-api-v3`（Bun/Hono）で **`bun test`** | `shiftapp-web` は **Playwright（E2E）のみ** |
| 本リポジトリ | API Routes / usecases / repositories で **Jest 427 件** | **テストなし**（受講者が作る部分） |

**「Jest か Playwright か」という比較は成立しません。層が違います。**
比べるべきはバックエンドのユニットテスト同士で、実アプリは Hono なので `bun test`、
こちらは Next.js の API Routes なので Jest。**土台が違えばテスト基盤が違うのは自然**です。

### 427 件は受講者のためのものではない

「**受講者が触ってはいけないバックエンド**」を守る安全網です。
受講者や Dependabot がそこを壊したときに CI が気づくためのもので、
**CI を導入した主目的そのもの**です。

受講者はテストを書きも読みもしないので、**フレームワークの選択に教育上の影響はありません。**

### bun へ移行しない理由

パッケージ管理とタスクランナーは bun にしていますが、テストだけ Jest のままです。
**「面倒だから残した」のではなく、次の 3 つが揃っているためです。**

**① そもそも「揃える」対象が存在しない**

bun を入れた目的は「実アプリと道具立てを揃える」ことでした。
しかし上表のとおり、実アプリのフロント（`shiftapp-web`）にも Jest はありません。
バックエンドのテストは実アプリでは Hono の別サービス、こちらは Next.js の API Routes。
**土台が違うので、同じにしようがない**というのが実際のところです。

**② 現時点では技術的にできない**

`bun test` は **`jest.mock()` を実装していません**
（[oven-sh/bun#29834](https://github.com/oven-sh/bun/issues/29834) が未クローズ）。
本リポジトリは `jest.mock` を **55 箇所・20 ファイル**で使っており、
テスト全体のモック戦略そのものです。1 ファイルを直せば済む話ではありません。
`jest.requireActual`（2 箇所）には**代替がありません**。

代替候補の `mock.module()` は **`jest.mock()` と違ってホイストしません**。
置換して終わりではなく、モック対象より先に読み込ませる形へ
**20 ファイルそれぞれを組み替える設計変更**になります。

**③ 効果がゼロで、リスクだけがある**

上記のとおり受講者はテストに触れないため、移行しても教育上の効果はありません。
一方で大規模なテスト書き換えは、**「緑になったが、実は前より検証していない」**状態を
作りやすい。守るための安全網を弱めるリスクだけを負うことになります。

> **やらない判断ではなく、今はやらない判断です。**
> Issue #29834 が解決したら見直してください。
>
> なお `bun run test` は shebang を尊重するので、内部では node + Jest で実行されます。
> **移行漏れではなく意図した構成**です。

## 9. 教材を修正するとき

教材（`.docs/curriculum/`）とコード（`reference/v3-complete`）は**内容を一致させてください**。
教材のコード例が実装と食い違うと、受講者はそのとおり書いて動かず詰まります。

修正したら:
1. `reference/v3-complete` で実際に動くことを確認する
2. 教材を同じ内容に更新する
3. **`main`（スターター）にも教材の変更を反映する** ← 受講者が読むのはこちら
4. 各教材のフッター（Document Version / Last Updated）を更新する

> ⚠️ 3 は**同一コミットを cherry-pick してペアで PR を出す**のが確実です。
> 両ブランチは別々に保護されているため、片方だけマージすると乖離します。
> 依存更新に伴う教材修正の場合は §7 の④も参照してください。
